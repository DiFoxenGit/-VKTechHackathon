# Архитектура

## Границы слоёв

| Модуль | Ответственность |
|---|---|
| `designer/app.py` | HTTP: загрузки, валидация, CORS, общий токен, шаблоны, материалы, задачи, ревизии, экспорт. Схемы запросов — `models.py`. `DESIGNER_DOCS=0` снимает Swagger, ReDoc и `openapi.json` с публичного сервера. |
| `designer/storage.py` | SQLite с атомарной записью JSON, исходные PPTX и артефакты на диске. UUID не зависит от имени файла, SQL параметризован, пользовательские имена не превращаются в пути. |
| `designer/parsing.py` | Разбор шаблона в дизайн-систему. Ни одного обращения к модели. |
| `designer/generation.py` | Бриф и материалы → валидированная `Outline`; контекстуальный аудит; аудит по картинке; сокращение перегруженных слайдов. |
| `designer/language.py` | Проверки письменности: язык колоды, подписи не на том языке, допустимая латиница (KPI, API, Q1). Общие для планирования и аудита. |
| `designer/layout.py` | Общая структура + шаблон → три геометрические модели. |
| `designer/visuals.py` | Нативные схемы и пиктограммы: процесс, цикл, пирамида, таймлайн, сравнение; библиотека иконок как композиций автофигур. |
| `designer/audit.py` | 26 детерминированных правил, контекстуальный аудит текста, аудит по изображению слайда, применение исправлений. |
| `designer/exporting.py` | Нативный PPTX, PDF через LibreOffice, HTML из SVG-страниц, рендер слайдов в PNG, измерение фона. |

## Что извлекается из шаблона

`parsing.py` строит паспорт дизайн-системы, а не список картинок:

- **Токены**: гарнитуры, типографическая шкала, палитра, цвета темы.
- **Типографика по умолчанию**: `p:txStyles` мастера и `a:lstStyle` каждой рамки — кегль, начертание, выравнивание и отступы берутся оттуда, а не из констант.
- **Геометрия**: рабочая область, внешние поля, вертикальные направляющие.
- **Паттерны**: каждый слайд-образец с его текстовыми слотами, ролью (`cover`, `agenda`, `section`, `team`, `closing`, `content`), площадью декора, фоном и рамками брендинга, которые обязаны пережить клонирование.
- **Фон**: объявленный в XML (заливка, градиент, картинка) и — отдельно — **измеренный**: страница рендерится в маленький PNG, считается яркость и разброс. XML часто «лжёт» (тёмное фото поверх белой заливки), а по измерению видно, нужна ли подложка под текст.

Слабый шаблон — это нормальный вход: если ролей не распозналось, слотов мало или страницы захламлены декором, набор кандидатов расширяется правилами послабления, а композиция опирается на рабочую область и шкалу.

## Пайплайн

```
шаблон ─┐
         ├─→ паспорт дизайн-системы ─┐
материалы┘                            ├─→ Outline ─→ classic / split / focus ─→ аудит ─→ нативный PPTX ─→ правки → новая ревизия ─→ PDF / HTML
                                     каркас повествования
```

1. **Материалы → контекст.** Тексты бьются на фрагменты, отбираются по релевантности брифу, бюджет — 24 000 символов (`DESIGNER_CONTEXT_CHARS`).
2. **Каркас повествования.** `prompts/narratives.v1.json` задаёт последовательность смыслов для назначения колоды (проект, фича, продукт, инициатива). Слайд о команде появляется только там, где он уместен и в материалах есть о ком рассказывать.
3. **План до вёрстки.** Модель возвращает структуру: заголовки, тезисы, визуализации, ссылки на источники. Проверяется число слайдов, ссылки на реальные материалы, единый язык подписей, отсутствие выдуманных чисел, дубли заголовков.
4. **Баланс по вместимости.** `slide_capacity` считает, сколько символов вмещает контентная область **этого** шаблона. Перегруженные слайды уходят агенту `condense`; если модель недоступна, текст подрезается детерминированно.
5. **Композиция.** Для каждого слайда выбирается паттерн шаблона (см. ниже), из него берутся слоты, кегли, выравнивание и вертикальный ритм. Ряд одинаковых рамок распознаётся как карточная сетка, и тезисы раскладываются по карточкам.
6. **Аудит в конвейере** — до того, как пользователь увидит результат.
7. **Экспорт.** Исходный PPTX клонируется с мастерами, макетами и рисунками; текст, таблицы, диаграммы и фигуры добавляются нативными объектами. `verify_pptx` открывает результат и подтверждает, что слайды состоят из редактируемых объектов.

Одна Outline применяется ко всем трём вариантам без изменения фактов. Различаются положение блоков, колоночность и размер области акцента; палитра, гарнитура и шкала — общие, из исходного файла.

## Выбор паттерна

Каждому слайду сопоставляется страница шаблона, и выбор объясним вслух:

- **Роль против назначения**: обложка получает страницу с ролью `cover`, финал — `closing`, контентный слайд теряет очки за обложку, оглавление и визитку команды.
- **Декор в рабочей полосе** штрафуется с коэффициентом 5: дешевле взять другую страницу, чем воевать с косой линией геометрией.
- **Фон**: страница с фотографией во весь слайд — раздел, а не место для текста.
- **Карточная сетка** под число тезисов даёт бонус, несовпадение — штраф.
- **Повтор** соседней страницы и каждое следующее использование дорожают, поэтому колода расходится по страницам, которые шаблон реально предлагает.

## Читаемость

Цвет текста выбирается из палитры шаблона по контрасту к **измеренному** фону один раз, и вёрстка, экспорт и аудит используют одно и то же решение. Если фон тёмный и пёстрый, под текст кладётся полупрозрачная подложка цвета фона — не белый прямоугольник поверх дизайна.

## Аудит

Три уровня, все внутри конвейера:

- **Детерминированный** (`audit.py`): выход за поля, пересечения, контраст, заполненность, кегль, длина заголовка, осиротевшие блоки, наезд на брендинг шаблона, соответствие чисел источникам. Элементы, пришедшие из шаблона (`from_template`), из части проверок исключены: их поставил дизайнер.
- **Контекстуальный** (текст): соответствие брифу, логика, тональность, поддержка чисел материалами.
- **По изображению**: слайд рендерится в PNG и уходит мультимодальной модели с вопросами «да/нет» о композиции, читаемости и соответствии шаблону.

Исправления применяются только по выбранным ID; после изменения проверки пересчитываются, неустранённая проблема остаётся в отчёте.

## Версионирование

`designer/prompts/manifest.json` хранит версию воркфлоу, файлы агентов и changelog с причиной каждого изменения. В задачу и презентацию пишется снимок: версия, sha256 каждого промпта, идентификатор модели. Любую колоду можно связать с тем, чем она сделана.

## Выполнение

Две одновременные генерации, максимум 20 активных или ожидающих задач. Обращения к модели асинхронные, тяжёлый экспорт PPTX — в потоке. Таймаут генерации 300 секунд после входа в слот; синхронный экспорт в потоке нельзя остановить таймаутом Python, поэтому предел не является жёсткой гарантией.

Задачи persistent по статусам, но не resumable: при перезапуске незавершённые помечаются ошибкой. Продакшн с несколькими процессами потребует внешней очереди и распределённых блокировок; текущий compose запускает один worker.

Ревизии неизменяемы на диске (`r1.pptx`, `r2.pptx`…) и пишутся после успешного экспорта. `revision` в PATCH и в применении исправлений даёт оптимистическую блокировку (409 при конфликте). PDF и HTML собираются во временном профиле LibreOffice и кешируются по ревизии.
