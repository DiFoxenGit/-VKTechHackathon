## Решение по страницам

Для финального боевого примера выбираем **13 страниц: одна обложка + 12 проверенных содержательных**. Это внутри диапазона 10–15 из ТЗ, сохраняет доказательства и не требует перед защитой переписывать карту защищённых страниц.

В брифе и интерфейсе явно указываем **13**, счётчик и скачанные файлы должны показывать 13. Произвольный пользовательский запрос на 12 не является разрешением молча выдать 13. PR №93 сейчас добавляет обложку после планировщика и только предупреждает об увеличении: перед слиянием нужно сделать итоговый контракт количества явным (поддержать нужное число либо до запуска понятно объяснить ограничение бизнес-режима). Одного сообщения после готовности недостаточно.

Вариант Димы на 12 страниц — отдельная следующая оптимизация: объединить резюме/KPI с сохранением фактов, ссылок, ограничений и действий. Сейчас это proposal, не готовый layout. Статический JSON содержит факты конкретного примера; нельзя подставлять его текст вместо свежих данных текущего задания.

## Стёпе — следующий шаг

1. Подключить semantic_blocks именно из текущего `slide.notes`: role, answer, interpretation, next_step, fact_ids, action_ref, context_refs. Каждый блок отображать один раз; факты брать из текущего расчёта, не из semantic-review.json как шаблонного текста.
2. Доделать №93 с явным итоговым числом страниц и показать четыре рендера: фирменная обложка, KPI/резюме, региональные отклонения, действия/риски. Сравнение с исходным шаблоном обязательно; сейчас эти четыре страницы не приняты.
3. Учесть, что approved_titles содержит вопросы («Каковы результаты…», «Как менялась…»). Защита чисел улучшилась, но сам факт вхождения заголовка в допустимый список не доказывает выполнение требования заголовка-вывода. Для аналитических страниц предпочитать подтверждённое утверждение с фактом, для риска/действия — содержательную оговорку/предложение. Не возвращать обязательную цифру в любой заголовок.
4. В UI quality_checks показывать отдельно от создания файлов: unavailable/failed не равно passed; visible_text_only не является проверкой всей композиции.
5. Смысловой audit-fixture с fixable=false — ручная корректировка с повторной проверкой. Для демонстрации выбранного автоматического исправления нужен отдельный геометрический пример, который действительно поддержан кодом. Не объявлять ручной пример автоматическим успехом.
