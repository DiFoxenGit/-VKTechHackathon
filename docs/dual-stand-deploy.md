# Автодеплой двух стендов

Основной стенд: **http://158.160.225.35/**. Второй: **https://auto-sell.site/presentations/**.
Источник кода — GitHub `main`. SourceCraft остаётся отдельным remote и не определяет версию выкладки.

После push в `main` workflow `CI` сначала выполняет общие backend/frontend/layout-проверки,
затем независимо запускает две задачи доставки одного проверенного SHA. Ошибка одного
стенда видна отдельной красной задачей и не отменяет доставку на второй. У каждого стенда
своя блокировка последовательных деплоев; отмена уже начавшегося деплоя выключена.

| Настройка GitHub Actions | Основной 158 | Второй auto-sell |
| --- | --- | --- |
| Адрес, пользователь | `PRIMARY_DEPLOY_HOST`, `PRIMARY_DEPLOY_USER` | существующие `DEPLOY_HOST`, `DEPLOY_USER` |
| Приватный ключ | `PRIMARY_DEPLOY_SSH_KEY` | существующий `DEPLOY_SSH_KEY` |
| Проверенный host key | `PRIMARY_DEPLOY_KNOWN_HOSTS` | существующий `DEPLOY_KNOWN_HOSTS` |
| Включение | задан `PRIMARY_DEPLOY_HOST` | `DEPLOY_TARGET=autosell` |
| Environment | `production-primary` | `production` |

Значения секретов не входят в Git и логи. Старые секреты auto-sell не заменяются.
Оба ключа ограничены командой деплоя; по новому ключу основного сервера нельзя открыть
shell или пробросить порт. Проверка host key обязательна.

Необязательный `DESIGNER_RUNTIME_PROFILE` — JSON с разрешёнными модельными настройками
для auto-sell. Размещение в нём API-ключей требует явного согласия владельца.
Workflow передаёт профиль через stdin SSH, без аргументов командной строки и вывода.
`deploy/runtime_profile.py` принимает не более 64 КиБ, запрещает посторонние поля,
переносы строк и неподдерживаемые символы, атомарно обновляет `.env.autosell` с правами
600. Прежние generic/VLM-настройки сохраняются; VLM при необходимости закрепляется
за прежним endpoint/key. Перед обновлением сохраняется закрытый `server.env`;
при неуспешной доставке он восстанавливается. Пустой secret оставляет env побайтово
прежним. Строка `Runtime profile` в логе показывает только имена провайдеров, модели
и числовые лимиты; ключи, Project-ID и URL с параметрами не выводятся.

После первого внедрения нового драйвера auto-sell может понадобиться повтор его
задачи CI на том же SHA: предыдущая версия драйвера не читала профиль из stdin.

## Основной сервер

Приложение: `/home/administrator/vk-designer`, Compose-проект `vk-designer`.
Закрытый runtime: `/home/administrator/vk-designer-runtime`.
При bootstrap устанавливаются версии `deploy/primary-receive.sh` и
`deploy/primary-deploy.sh` в runtime с правами 700. Строка отдельного публичного CI-ключа
в `authorized_keys` использует `restrict,command="bash /home/administrator/vk-designer-runtime/primary-receive.sh"`.
Существующие SSH-ключи сохраняются. Bootstrap выполняется административным ключом,
приватная часть нового CI-ключа после регистрации в GitHub удаляется с рабочих машин.

Приёмник принимает только `deploy <40 hex>`, блокирует одновременные деплои и вызывает
закрытую runtime-копию драйвера. После успешной выкладки драйвер атомарно обновляет
свою runtime-копию из принятого коммита. При изменении самого приёмника его bootstrap
нужно повторить отдельно.

Драйвер явно получает `main` из GitHub, проверяет принадлежность SHA основной ветке
и отсутствие правок отслеживаемых серверных файлов. Старый CI-запуск не откатывает
уже установленный более новый коммит. `.env` и секретный `genapi.compose.json`
сохраняются, последний всегда передаётся третьим Compose-файлом. Backend и frontend
собираются последовательно с `umask 022`; исходники читаются непривилегированным
пользователем контейнера. Порты, Caddy, тома и SSH-служба не перенастраиваются.

Перед перезапуском проверяется отсутствие заданий `queued/running` и выполняется
SQLite backup API. Если есть активное задание, деплой прекращается: повторить CI после
его окончания. Это проверка перед перезапуском, а не полноценный режим остановки
приёма новых заданий; запись демо и деплой следует разводить по времени.
При сбое сборки старые контейнеры продолжают работать; при сбое запуска/healthcheck
восстанавливаются прежний checkout и образы. База автоматически назад не откатывается.

Резерв окружения и контрольная сумма override: `runtime/deploy-backups/<UTC>/`,
резерв базы: `/data/deploy-backups/<SHA>-<unique>.sqlite3` в существующем томе.
Прежние образы получают теги `before-<SHA>`. Автоматического удаления резервов нет.
Установленный SHA: `runtime/deployed-main.sha`; финальная строка Actions:
`Deployed <SHA> to primary http://158.160.225.35/`.

Оба драйвера используют общий `deploy/backup_database.py` для согласованного снимка
SQLite и отказа при активной генерации. Исходная база открывается только для чтения;
отсутствующая база не создаётся. На auto-sell при сбое до рестарта также сохраняются
работающие контейнеры, а резерв базы находится в его собственном томе `/data`.

## Проверка

`backend/tests/test_primary_deploy.py` выполняет Linux shell с подменёнными git/Docker:
проверяет запрет произвольных SSH-команд, чужого SHA и локальных правок, порядок сборок,
сохранение окружения, отказ перед рестартом при активном задании, откат после плохого healthcheck.
Тесты не подключаются к серверам и не вызывают модели. Живое подтверждение автодеплоя —
две зелёные задачи доставки на одном push в `main` и `/health` обоих стендов.

Доставка одинакового кода не выравнивает закрытые модельные настройки. Профили ВК,
GenAPI и изображений проверяются отдельно; `llm_configured=true` доказывает только
наличие настроек, успешный вызов подтверждается trace конкретной генерации.
