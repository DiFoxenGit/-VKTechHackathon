фотографией на втором слайде справа. Совпадают исходный бриф, структура, текст,
исходный PPTX-шаблон и настройки. Основная редактура текста выключена: готовая
структура из трёх слайдов позволяет измерить добавку image-пути, не смешивая её
с разбросом текстовой модели. План изображений, VLM-проверка и обычная сборка включены.

Одна пара — наблюдение, не p95 и не гарантия SLA. Время планирования различалось,
изображения создавались отдельными задачами провайдера; по этим данным нельзя
объявить один сервер стабильно быстрее. Результат не переносится на 12 слайдов,
несколько картинок или общую бизнес-приёмку S8/S9. Раздельное время собственно
GenAPI, VLM и сохранения ассета не инструментировалось; прибавка включает весь image-путь.
Для сценария с запрошенными изображениями их ожидание включаем в таймер 300 с;
время до скачанного PDF указываем дополнительно, без переноса image-работы за таймер.

Машинные доказательства: [image-timing-2026-10-20.json](../samples/provider-contracts/image-timing-2026-10-20.json).
Режимы инструмента [check_image_timing.py](../tools/check_image_timing.py):
по умолчанию dry-run; `--live` создаёт задания; `--verify-only` проверяет ранее созданные
PPTX только GET-запросами. Наличие отчёта блокирует повторный `--live`, в том числе
после таймаута или ошибки: сначала проверить сохранённые job ID. Не менять путь
отчёта ради повторной платной отправки.

## Что удалось подтвердить о лимитах

Проверены официальные [очередь](https://gen-api.ru/docs/queue),
[sync](https://gen-api.ru/docs/synchronous-requests),
[Gemma API](https://gen-api.ru/model/gemma-4/api),
[Z-Image API](https://gen-api.ru/model/z-image/api),
[цены/контекст](https://gen-api.ru/pricing),
[GET user](https://gen-api.ru/docs/v1/user/user-information),
[жизненный цикл генераций](https://gen-api.ru/docs/generation),
публичная главная и поиск документации.

| Вид ограничения | Подтверждение |
| --- | --- |
| Gemma 4 31B: максимальный выход / контекст | В публичной таблице GenAPI — 128 000 / 262 144 токена; это модельные параметры, не скорость или квота аккаунта. |
| Режим Gemma | `is_sync` есть, по умолчанию false. Sync рекомендован коротким задачам; подтверждённого ускоренного режима длинного бизнес-запроса не найдено. |
| Долгие задания | Очередь и получение результата по request ID. Ожидание processing само по себе не раскрывает длину очереди и не доказывает достигнутый hard limit. |
| Срок доступности файлов / полных результатов | В официальном разделе генераций — 24 часа / 14 дней. Сервис скачивает PNG сразу и хранит свою копию, поэтому экспорт не зависит от дальнейшей жизни временного URL. |
| Квота одновременных запросов / RPM / TPM аккаунта | В проверенных источниках числовая квота не раскрыта. GET user не возвращает этих полей, rate-limit/Retry-After-заголовков в успешном ответе не было. |
| Денежное ограничение организации | В ответе API `organization.rub_limit=null`, `rub_remaining=null`. Это не доказательство отсутствия лимитов конкурентности. Идентификаторы, имена, контакты и токены организации не сохранялись. |

Не проводились платные нагрузочные пробы, провокация 429 и сравнение sync/async
на повторных оплаченных запросах. Наблюдение 19 октября «две Gemma проходили,
три зависали» не превращаем в доказанную квоту 2.

Рабочая рекомендация остаётся: `DESIGNER_MAX_JOBS=2`, GenAPI fallback 220 с,
image-адаптер 150 с, опрос раз в 2 с, без повторного POST после транспортного сбоя.
Все эти значения — наши настройки. Локальный семафор одного backend не ограничивает
общий аккаунт двух стендов; короткая проверка не является общим rate limiter.
Для демо избегать одновременных нагрузочных запусков двух стендов.
