# Финальная интеграция аналитики

Дата: 17 октября 2026. Актуальная интеграция модуля Димы, API и проверки: [dima-service-integration.md](dima-service-integration.md). Исторические замеры ниже относятся к первому автономному прогону. Все примеры в `samples/final/` синтетические.

## Запуск и воспроизведение

1. Установить зависимости backend из `backend/requirements.txt` и frontend командой `npm ci` в `frontend/`.
2. В серверном `.env` задать `DESIGNER_LLM_PROVIDER=vk`, `DESIGNER_VK_BASE_URL`, `DESIGNER_VK_MODEL=qwen38-27b-fp8`, `DESIGNER_VK_API_KEY`, `DESIGNER_VK_PROJECT_ID`. Не переносить эти значения в `VITE_*`.
3. Запустить `python tools/run_final_server.py`, затем `npm run dev` в `frontend/`. Для локального PDF установить LibreOffice; необязательный `DESIGNER_SOFFICE` указывает на `soffice`/`soffice.com`. Docker backend уже содержит конвертер.
4. Загрузить исходный PPTX-шаблон организаторов. Добавить несколько материалов и отдельно брендбук. Поле «Цель анализа» у файла необязательно: например, «Динамика», «Доли каналов», «Распределение суммы», «Взаимосвязь», «Справочная таблица».
5. Нажать «Проверить данные»: увидеть профиль, выбранный тип, допустимые альтернативы, предупреждения и происхождение значений. При отказе уточнить задачу, колонки и известную единицу в появившихся настройках и проверить повторно.
6. Создать презентацию и скачать PPTX/PDF. Для всех семи наборов со справочной таблицей на 240 строк задать 30 слайдов. Вместо заполнения пустых слайдов сервис выпускает только страницы с данными.

## Что реализовано

S1: отдельный VK-профиль, обязательный `Project-ID`, серверный ключ, compose-переменная, схема ответа и отказ при обрезанном ответе. `tools/check_final_inference.py` проверяет реальный клиент и планировщик.

S2: нативные редактируемые таблицы, bar, line, pie, scatter, histogram, grouped_bar, stacked_bar и KPI. Пропуски линии остаются разрывами. Источник выводится на слайде. Таблицы разбиваются с повторением заголовков. Есть браузерные SVG-превью и нативный локальный PPTX после правок.

S3: `analytics/` содержит модуль Димы и контракт `AnalysisResult 1.0`; `analytics_bridge.py` подключает его к сервису без повторной реализации вычислений. Полные таблицы и оригинальные байты остаются на сервере; отбор текстового контекста не ограничивает расчёты. Числа считает Python. Варианты оформления используют один результат. До и после вёрстки проверяются категории, значения, источник и заголовок. Подмена значений в API-правке возвращает 422. Общий список разрешённых чисел не используется как доказательство расчёта. Контекстный аудит опционален, детерминированная проверка аналитики обязательна.

S4: XLSX и ZIP, несколько материалов со списком и индивидуальным удалением, цель анализа по файлу, отдельный брендбук, объяснения и причины отказа.

S5: JSON-токены (`name`, `colors`, `font`, `background`, `text_color`, `title_size`, `body_size`), ограниченный текстовый PDF и ZIP с `brandbook.json`. Приоритет API: `style_overrides` → брендбук → шаблон → безопасные значения. Брендбук создаёт чистую страницу, чтобы оформление/логотипы старого мастера не противоречили новым правилам. Без брендбука сохраняются страницы исходного PPTX-шаблона.

S6: автоматические регрессии, реальные HTTP-прогоны, открытие нативных PPTX, конвертация PDF через LibreOffice, сравнение другого шаблона и изменённого источника. Отчёты и файлы находятся в `output/final/` и не попадают в Git.

S7: семь воспроизводимых датасетов (`python tools/make_final_samples.py`), независимые контрольные ответы, два JSON-брендбука и ZIP. Текущий браузерный сценарий — `frontend/scripts/qa-dima-integration.cjs`, HTTP-приёмка — `tools/check_analytics_integration.py`. Запись прежнего автономного прогона сохранена в `output/final/` как исторический материал.

## Границы реализации

- Детерминированный модуль Димы поддерживает явно заданные задачи, измерения, метрики, фильтры и агрегации. Неоднозначные случаи возвращают отказ; интерфейс позволяет уточнить параметры. Подробная спецификация — `analytics-contract.md`.
- Даты: ISO, YYYY-MM, DD.MM.YYYY, год и стили XLSX. Неоднозначные slash-даты не угадываются. Иерархии — наблюдаемые функциональные зависимости, а не гарантированная бизнес-семантика.
- Проценты без весов не агрегируются. Выбросы по 1.5 IQR сохранены. Интервалы гистограммы считаются модулем; пользователь может явно задать bins через AnalysisRequest.
- Импорт: 100000 строк, 256 колонок, 1000000 ячеек и документированные ограничения ZIP. Графики получают страницы по 20 категорий без top-N/обрезки; экспорт поддерживает 8 серий, 2000 точек scatter и до 30 слайдов. При превышении возвращается объяснение.
- XLSX не вычисляет формулы: отсутствие кеша сохраняется как null с предупреждением. JSON и TXT/MD разбирает модуль Димы; все листы/таблицы хранятся целиком.
- PDF брендбука: только явно подписанные строки `Палитра: #RRGGBB, ...` и `Шрифт: ...`. Сканы, произвольная интерпретация PDF, автоматический разбор `.fig`, логотипы и визуальные примеры из ZIP не реализованы. Figma требует ручного экспорта токенов в описанную схему. Предупреждения показаны пользователю.
- Браузерный просмотр сохраняет данные и объяснения, но не воспроизводит все декоративные элементы корпоративного PPTX. Серверный экспорт использует исходный шаблон; при локальной правке экспорт использует оформление редактора. VLM не проверена и не объявляется обязательной.
- Скринкаст с русскими пояснениями фиксирует реальный локальный прогон с уже разобранными шаблонами; это не измерение холодного старта и не подтверждение production-выкладки. Финальная приёмка Андреем на другом устройстве остаётся отдельным действием команды.

## Проверки

```powershell
$env:PYTHONPATH='backend'
python -m pytest backend/tests -q
python tools/check_final_inference.py
python tools/check_analytics_integration.py --url http://127.0.0.1:8003/api/v1
cd frontend
npm run check
npm run build
```

`check_analytics_integration.py` использует настоящие загрузки и генерацию, сверяет контракт Димы, сравнивает данные трёх вариантов, открывает PPTX, проверяет PDF, другой шаблон и изменённый CSV. Перед запуском зарегистрируйте два шаблона через интерфейс. `check_final_acceptance.py` и старые замеры ниже относятся к автономному прогону до подключения Димы. `controls.json` рассчитан независимо от производственного аналитического кода. Пропуски старых тестов не считаются подтверждением соответствующих сценариев.
